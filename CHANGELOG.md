## [Unreleased]

### Changed

- `nas-model`, `provider-qnap`: a backup with a plan of its own is no longer reported „seit n Tagen nicht gelaufen“ after two days. `BackupTask::interval_secs` is the longest gap between two planned runs; the warning waits that gap plus one day, at least the two days of the threshold, so a weekly job warns after eight days and a daily one after two. The QNAP provider reads it from the cron lines of Hybrid Backup Sync 3 (daily, weekly on one or several days, monthly counted as 31 days, 62 days from the 29th on); a job started by hand or a plan it does not understand keeps the two days (#150).
- `stats-ffi`: HTTP 502, 503 and 504 count as „no answer“ like no connection and a time-out (`ProviderError::is_no_answer`), because a reverse proxy sends them when the NAS behind it is gone. After 15 minutes without a snapshot they open „nicht erreichbar“; other HTTP errors such as 500, a refused login, missing rights, a changed certificate and an unreadable answer still do not. `NasProblem` gets `noAnswer`, and the apps show „Nicht erreichbar“ (grey) from it instead of checking the kinds themselves (#112).
- `stats-ffi`: the core computes the findings with the thresholds the app sets (`NasCore::set_thresholds`, `demo_snapshots(now, thresholds)`, `standard_thresholds`) and recomputes them from the snapshot as read, so a changed threshold shows at once without a query, also for the snapshot of the test query of the add dialog, which the core takes over when the NAS is added. Snapshots name the volumes whose fill level counts (`capacity_volume_ids`). The apps take the findings of the core unchanged and no longer check fill level and disk temperature themselves (#85).

### Added

- App: „NAS hinzufügen“ and „Zugang ändern“ take an Unraid (#36). The dialog has a vendor choice: QNAP and Unraid can be chosen, Synology and TrueNAS stay „folgt“ until their providers deliver values (#157). For an Unraid it asks only for address and API key, hints at the role `VIEWER` (Unraid 7.2 or newer) and speaks of Unraid in refused-key, missing-rights and certificate texts instead of QTS. The card badge keeps the vendor name as text, no brand logos.
- `provider-synology`: login to Synology DSM (#31). The client reads paths and versions of the APIs from `SYNO.API.Info` and logs in over `SYNO.API.Auth` (DSM 6 or newer, form POST, session id in memory), renewing a session the NAS reports gone (106, 107, 119, HTTP 401) exactly once. The second factor is entered once (`SynologyClient::login_with_code`, with `enable_device_token`); the NAS issues a device token that the caller stores and passes back, so later logins need no code, and no TOTP secret is stored. Error 105 (account without admin rights) is „keine Rechte“ at once without a new login. A rejected login (400, 401, 402 and unknown codes, 403, 404, 406 for the second factor, HTTP 401 on the login) and a blocked IP (407, or HTTP 403 or 429 on the login or the catalog) stop every request until the user acts. The fixtures follow the DSM Login Web API Guide and NAS Pulse, not a real device. `nas_model::ProviderError::IpBlocked` („NAS hat diese Adresse gesperrt“) stops polling, reaches the apps as `FfiError::IpBlocked` and `ProblemKind::IpBlocked`, and the add dialog and „Zugang ändern“ in the settings show their own text with the way to unblock the address in DSM instead of „Passwort falsch“. Storing the device token and entering the code in the app follow with #36, the data requests with #32.
- `provider-unraid`: Unraid 7.2 and newer over the GraphQL API with an API key of the role `VIEWER` (header `x-api-key`, `NasClient::post_json_text_api_key`). The snapshot holds server, array with fill level and parity check, parity, data and cache disks with temperature, state and spin state (from `array` only, since the query `disks` wakes sleeping disks, so without SMART), shares, unread notifications, the UPS, containers, CPU and memory; a missing Docker service, UPS or right leaves only that part empty, a refused key is a refused login. The parity history becomes backup runs. Fields are read tolerantly and the queries use only fields of API 4.25 (Unraid 7.2.0); capacities are kilobytes of 1000 bytes. The core of the app (`connect`, password = API key) and the collector (`api_key` in `collector.toml`) take an Unraid; HTTPS only, so SSL must be on in Unraid (#35).
- `provider-qnap`: backup jobs of Hybrid Backup Sync 3 (#41). The provider reads them read-only over the REST interface of HBS 3 that its web interface uses (`GET /cc3/v1/users/system/jobs` with the QTS session in the header `X-QNAP-SID`, one request per query, no extra login) and puts the enabled backup jobs into the snapshot with name, start of the last run and result. Only the status `Finished` is known from a real NAS and counts as OK; every other status stays unknown and raises no failure warning. The next run stays unknown (cron in the time zone of the NAS). Without HBS 3, with HBS 3 stopped, without the right to read it or with an answer that is no JSON the list stays empty and the rest of the snapshot stays complete. The detail screen of a QNAP without jobs now shows „Hybrid Backup Sync: keine Aufträge gefunden“ instead of „Schnittstelle offen“. `nas-http`: `NasClient::get_text_with_headers`.
- `provider-qnap`: the UPS on the NAS (state, charge, remaining runtime) from `devices/devRequest.cgi?subfunc=ups`, so the UPS section of the detail page and the finding „USV auf Batterie“ work for QNAP. `ups_status` follows the NUT flags (`OB` is on battery, `OL` online, other text leaves the state empty); without a UPS (`--`), with an HTTP error or without the right the UPS stays empty. `qnap-capture` records the page and replaces the SNMP community in it (#146).
- `provider-truenas`: connection and login for TrueNAS 25.04 and later over JSON-RPC 2.0 on `wss://<host>/api/current` (#33), not the REST API that TrueNAS 27 drops. The WebSocket runs over the confirmed certificate (`nas_http::connect_pinned`, new, with `peer_certificate`); `http://` and `ws://` are refused before any connection, because TrueNAS revokes a key sent without TLS. Access is user name and API key (`TruenasCredentials`, advice `ROLE_HINT`: a user of its own with the role `READONLY_ADMIN`). When `auth.mechanism_choices` offers SCRAM (TrueNAS 26), the client logs in with SCRAM-SHA-512 bound to the certificate (`tls-server-end-point`), so the key never goes over the wire; otherwise it sends the key over TLS (`API_KEY_PLAIN`). A rejected or expired key, a wrong server signature and a required second factor block every further connection until new credentials; a redirect to the other controller does not. `Session::call` calls any reading method (20 s per call, answers matched by `id`, events skipped). Tested against a fake TrueNAS and messages of the official TrueNAS client library; pools, disks and alerts follow in #34.

- `stats-core`: forecast "full in X days" per volume (`forecast`, `HistoryStore::forecast`). A least-squares line runs through the daily values of the used space of the last 30 days; it needs at least 7 daily values (gaps do not count, the line uses the real distances) and a rising line, otherwise there is no trend (`None`), also when the volume would be full only after more than 10 years. The days are counted from the point of the line at today, not from the last value, so a large cleanup does not make the forecast jump; a line above the size of the volume gives 0 days. Result: days to full, date and growth in bytes per day. The demo data give DataVol1 "full in 143 days" (143.08 from the line); the apps round the days, the display follows with #67 (#9).
- `nas-model`: events from changes of state. `detect_events` compares a snapshot with the open events (not with the previous snapshot) and returns opened, raised and closed events for alerts, disks, volumes, fans, UPS and backups, with hysteresis (disk 3 °C, volume 1 point below the threshold; a fill event opens at 80 % and rises to critical at 90 %). `detect_unreachable` opens „nicht erreichbar“ after 15 minutes without a snapshot. `nas-demo` carries the events of the mockup (#10).
- `stats-core` crate: history archive in SQLite (`HistoryStore`). Each snapshot writes used and total space per volume, temperature per disk, CPU, memory, system temperature and throughput per interface, plus the last run of each backup task (a finished run does not go back to running). Every write rebuilds the touched UTC hours (min, mean, max) and days (a day older than the hourly values keeps its daily value) and prunes: raw samples after 7 days, hourly values after 90 days, daily values, backup runs and events never. `history` returns every sample for 24 hours, hourly values for 7 and 30 days and daily values for 1 year; events (#10) are stored with start and end (`write_events`) and the open ones per NAS are loaded for the detection after a restart (`open_events`); schema version 1 with stepwise migrations (#8).
- `stats-core` crate: polling planner that queries each NAS at most every 5 minutes (a longer interval may be set), keeps the last snapshot with error time and error on failures, retries after a network error only at the regular time, blocks a NAS after a rejected login, second factor or changed certificate until it is unblocked, and allows a manual refresh 30 s after the last query. It takes the last query time and the block the app remembers, hands every finished query to a `PollSink` and runs on tokio; tested with paused time and a fake provider. The apps are not connected yet (#60) (#11).
